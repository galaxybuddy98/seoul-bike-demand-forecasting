# 공간 수요 예측 프로젝트 설계

## 의도

서울시 공공자전거(따릉이)의 지역·시간별 수요를 분석하고 예측해 데이터 엔지니어링, GIS, 머신러닝, 딥러닝, 서비스화 역량을 보여주는 취업 포트폴리오를 만든다. 대여소별 시간 단위 수요를 핵심 예측 문제로 삼고 외부 영향요인의 기여를 비교한다.

## 목표

- 공식 출처에서 확인한 공공자전거·대여소·날씨·공간경계 데이터를 재현 가능하게 적재한다.
- PostgreSQL/PostGIS에서 시공간 데이터 모델과 공간 조인을 구현한다.
- GeoPandas와 QGIS로 결과를 검증하고 시각화한다.
- 단순 베이스라인, scikit-learn, LightGBM, PyTorch LSTM을 동일한 시간 기준으로 비교한다.
- FastAPI와 Streamlit으로 배치 예측과 지도 기반 인사이트를 전달한다.

## 범위 밖의 목표와 지양할 방향

- 첫 버전에서 다도시, 실시간 운영, 자동 재학습, 클라우드 배포, 모바일 앱을 지원하지 않는다.
- 재배치 최적화와 인과 추론은 후속 과제로 둔다.
- 확인하지 않은 데이터셋, 컬럼, 보존 기간, API를 존재한다고 가정하지 않는다.
- LSTM이 LightGBM보다 좋아야 한다는 결론을 미리 정하지 않는다.
- 기술 목록을 위해 마이크로서비스나 불필요한 추상화를 추가하지 않는다.
- 무작위 시간 분할이나 미래 통계가 섞인 특징으로 성능을 부풀리지 않는다.

## 제약사항

- 단계는 SQL/GIS -> 머신러닝 -> 딥러닝 -> API/대시보드 순서로 진행한다.
- 오늘은 설계 문서와 최소 폴더 구조만 만든다.
- 오늘은 패키지 설치, 데이터 다운로드, 모델 학습, 외부 API 호출, GitHub Push를 하지 않는다.
- 대상 도시는 서울로 하되 실제 따릉이·기상·행사·공간 데이터는 공식 문서로 출처, 필드, 기간, 라이선스를 검증한 뒤 사용한다.

## 검토한 접근법

### A. 단일 도시·대여소×시간 예측 — 선택

대여소별 시간당 대여 건수를 주 목표로 삼고 필요하면 반납 건수를 보조 목표로 확장한다. 관측 단위가 명확하며 PostGIS 공간 조인, 시계열 특징, 지도 표현을 자연스럽게 연결할 수 있다.

### B. 격자×시간 예측

행정동 또는 정규 격자 집계는 GIS 비중이 크지만 격자 크기와 희소성 처리 근거가 추가된다. 선택안에서는 대시보드용 집계 뷰로만 활용한다.

### C. 다도시 비교

일반화 비교가 가능하지만 식별자, 시간대, 라이선스, 운영 규칙 정규화가 핵심 분석보다 커질 수 있어 후속 확장으로 남긴다.

## 아키텍처

공식 원천 데이터 -> 원본 검증·보존 -> Pandas/GeoPandas 정제 -> PostgreSQL/PostGIS(raw, staging, mart.station_hour) -> 특징 데이터셋 -> seasonal naive/scikit-learn/LightGBM/LSTM -> 예측 결과 -> FastAPI -> Streamlit.

QGIS는 공간 품질검사와 정적 지도 제작에 사용한다. 하나의 PostgreSQL 인스턴스와 하나의 Python 코드베이스를 사용하며 데이터베이스 스키마는 계보를 위한 최소 경계다.

## 분석 기준

- 기본 관측 단위: station_id × hour.
- 주 목표 후보: 해당 시간에 시작된 대여 건수 pickup_count.
- 보조 목표 후보: 반납 건수 return_count.
- 대여소 식별자 안정성과 변경 이력을 확인한 뒤 실제 키를 확정한다.
- 운영 중지·신설·이전은 유효기간이 있는 대여소 차원으로 표현하는 방안을 우선 검토한다.
- 원천 시간대와 일광절약시간 적용 여부를 확인한다.
- 통합 geometry는 원칙적으로 EPSG:4326을 사용하고 거리 계산용 지역 투영 CRS는 도시 확정 후 선택한다.

## 데이터 출처 조사 계획

### 검증 순서

1. 대상 도시 공공데이터 포털 또는 운영기관 공식 페이지에서 이용 이력 제공 여부를 확인한다.
2. 데이터 사전, 샘플, 갱신 주기, 보존 범위, 파일/API 방식, 약관과 라이선스를 기록한다.
3. 대여소 마스터의 좌표, 식별자, 운영 상태와 변경 이력을 확인한다.
4. 공식 기상기관에서 시간 단위 날씨와 관측소 위치를 확인한다.
5. 공식 공간정보 기관에서 행정경계 기준일, CRS, 라이선스를 확인한다.
6. 작은 샘플을 수동 검토한 뒤에만 실제 컬럼명을 데이터 계약으로 승격한다.
7. URL, 조회일, 버전·기준일, 라이선스, 원본 체크섬을 데이터 카탈로그에 기록한다.

### 확인 전 조사 후보

- 공공자전거 운영기관 또는 지자체의 대여·반납 이력.
- 같은 기관의 대여소 위치·상태 마스터.
- 공식 기상기관의 시간별 관측 또는 예보 이력.
- 공식 공간정보 기관의 행정경계.
- 정부가 공표한 달력 또는 검증 가능한 공휴일 규칙.

현재 이용 가능성이나 필드를 보장하지 않는다. 비공식 복제본은 공식 원천 이해를 돕는 참고 자료로만 취급한다.

### 확인할 필수 의미 필드

| 영역 | 필요한 의미 필드 | 확인할 질문 |
|---|---|---|
| 대여 이력 | 대여 시작시각, 출발 대여소 ID; 선택적으로 반납시각과 도착 대여소 ID | 이벤트/집계 단위, 취소 기록, 시간대 |
| 대여소 | 대여소 ID, 이름, 좌표/geometry; 가능하면 유효기간과 상태 | ID 재사용, 이전·폐쇄 이력, CRS |
| 날씨 | 관측시각, 기온, 강수량; 선택적으로 습도, 바람, 적설 | 관측/예보 구분, 결측·누적 규칙, 관측소 연결 |
| 공간경계 | polygon geometry, 지역 코드/이름, 기준일 | 기준일, CRS, 재배포 조건 |
| 달력 | 지역 날짜, 요일, 공휴일 여부/이름 | 임시·대체공휴일 재현성 |

필수 의미 필드가 공식 자료에서 확인되지 않으면 해당 분석이나 특징을 제외하거나 목표를 조정한다.

## 데이터 및 GIS 설계

- raw: 원천 행과 출처, 수집 시각, 체크섬을 보존한다.
- staging: 형 변환, 시간대 정규화, 식별자 정리, 품질 플래그를 적용한다.
- mart: 대여소 차원, 시간 차원, 대여소×시간 수요, 공간 집계, 모델 예측을 제공한다.
- 대여소 geometry 유효성과 좌표 범위를 검사한다.
- 경계 포함 규칙을 명시한 PostGIS 공간 조인으로 행정구역을 부여한다.
- 관측소 연결은 거리, 행정구역, 공식 매핑 중 검증 가능한 방식을 선택한다.
- 경계선 위 점, 누락 좌표, 중복 위치는 품질 리포트에 집계한다.

## 데이터 누수 방지 원칙

- 캘린더 특징과 t-1, t-24, t-168 수요 lag 후보를 사용한다.
- rolling 통계는 한 시점 이상 shift한 값으로 계산한다.
- 날씨는 실제 예측 시점에 이용 가능한 정보만 사용한다. 사후 관측 날씨 실험은 upper-bound로 별도 표시한다.
- 대치, 스케일링, 인코딩, 특징 선택은 학습 구간에만 fit한다.
- 전체 기간이나 테스트 기간에서 계산한 대여소 평균, 순위, 군집을 특징으로 사용하지 않는다.

## 개발 단계

### 1단계: SQL/GIS

원천 품질 검사, 시간 집계, 대여소 차원, 행정구역 공간 조인, 시공간 EDA를 완성한다. 결과는 mart.station_hour와 품질 리포트다.

### 2단계: 머신러닝

지속성·평균, 전일·전주 동일 시간 seasonal naive, Random Forest, LightGBM을 같은 분할과 메트릭으로 비교한다.

### 3단계: 딥러닝

PyTorch LSTM은 과거 수요 시퀀스와 검증된 외생 특징을 입력으로 사용한다. 시퀀스 길이와 대여소 표현은 데이터 규모 확인 후 정한다. ML보다 나쁜 결과도 숨기지 않고 비용과 안정성까지 해석한다.

### 4단계: API와 대시보드

FastAPI는 건강 상태, 대여소, 시간 범위별 사전 계산 예측을 읽기 전용으로 제공한다. Streamlit은 시간·지역 필터, 지도, 실제값 대 예측값, 모델 비교, 오차 상위 대여소를 보여준다.

## 외부 영향요인 비교

- Model A: 시간·요일·계절과 과거 수요.
- Model B: Model A + 예측 시점에 이용 가능한 기상과 공휴일.
- Model C: Model B + 지하철·주요시설 거리 등 GIS 특징과 검증된 행사 정보.
- 행사 자료는 과거 snapshot, 취소·변경 이력, 시간·장소, 라이선스를 확인하지 못하면 Model C에서 제외한다.
- 사후 확정 관객수와 미래 실측 날씨는 운영 입력으로 사용하지 않는다.

## 평가 계획

- 오래된 연속 구간을 학습, 다음 구간을 검증, 가장 최근 연속 구간을 잠긴 테스트로 사용한다.
- 날짜와 길이는 데이터 범위, 계절성, 정책 변경일을 확인한 뒤 고정한다.
- 모델 선택은 테스트를 보지 않고 학습·검증 구간에서 수행한다.
- expanding-window 또는 rolling-origin backtest로 여러 예측 시작점을 평가한다.
- 신규 대여소는 cold-start 평가로 분리하거나 충분한 이력이 있는 대여소만 기본 평가에 포함하고 규칙을 공개한다.
- MAE를 주 지표로, RMSE를 피크 오차에 민감한 보조 지표로 사용한다.
- 전체 micro 평균, 대여소별 macro 평균, 시간대·요일·수요 분위별 오차를 보고한다.
- seasonal naive 대비 개선폭을 반드시 함께 보고한다.
- 분할 경계, 특징 기준 시점, 랜덤 시드, 모델 버전, 학습 종료 시점을 기록한다.

## 품질 및 오류 처리

- 필수 식별자나 타임스탬프가 없는 행은 임의 보정하지 않고 격리·집계한다.
- 중복 키는 실제 스키마 확인 후 정의한다.
- 음수 duration, 도시 밖 좌표, 비현실적 시간 값은 근거 있는 품질 규칙으로 처리한다.
- 원천 스키마 변경은 계약 검사 실패로 드러나게 한다.
- API는 잘못된 범위, 없는 대여소, 없는 예측에 명시적 오류를 반환한다.

초기에는 일반 검색과 명시적 경로를 사용한다. 모델 파이프라인, API, 대시보드 사이 심볼 추적이 어려워질 때 Serena를 도입한다. Python 언어 서버를 사용하고 src, tests를 주요 탐색 범위로 두며 데이터, 모델, 캐시는 제외한다.

## 위험요소와 대응

| 위험요소 | 대응 |
|---|---|
| 이벤트 이력이 제공되지 않음 | 확인 가능한 집계 단위로 목표를 재정의하고 제약 공개 |
| 대여소 ID나 위치가 변경됨 | 유효기간 차원을 검토하고 단순 덮어쓰기 금지 |
| 사후 날씨로 성능이 부풀려짐 | 예측 시점 가용성 적용, 관측 날씨는 upper-bound로 분리 |
| 0 수요와 피크 불균형 | MAE/RMSE 및 구간별 리포트 병행 |
| LSTM 복잡성 | LightGBM을 강한 기준으로 유지하고 시퀀스 실험 제한 |
| 범위 확장 | 단일 도시, 시간당 대여 수요, 배치 예측 조회로 첫 완료 기준 고정 |

## 데이터 조사 후 확정할 사항

- 서울시 따릉이 공식 자료의 제공기관과 데이터별 실제 공개 범위.
- 이용 이력의 관측 단위와 보존 기간.
- 예측 horizon과 집계 간격.
